# Host-Off results — 1 September 2026

This is an early measurement snapshot, not a permanent league table. Every listed mirror served the same 6,008-byte HTML fixture, and all tested fixture files matched byte-for-byte before measurement.

## What changed when the test became realistic

Twenty isolated requests made the platforms look almost identical: Cloudflare Pages had a 101 ms median TTFB, while the HostXNow 9950X account had 113 ms. An 11 ms gap is not a visitor-facing story.

The more useful tests were a modern multiplexed burst, a real 504 KB homepage, cold and warm browser loads, and the p95 tail rather than one best request.

## Neutral fixture: modest burst

Each result below is the median of three rotated trials. Each trial sent 60 requests with up to 12 in flight from one Dublin client. HTTPS targets used HTTP/2; the CX23 endpoint is currently HTTP/1.1 only. `p50`, `p95` and `p99` are complete-request times for the 6 KB fixture.

| Mirror | Protocol | Requests/s | p50 | p95 | p99 | Failures |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Cloudflare Pages | HTTP/2 | 178.6 | 40 ms | 126 ms | 143 ms | 0 / 180 |
| GitHub Pages | HTTP/2 | 164.9 | 43 ms | 146 ms | 147 ms | 0 / 180 |
| MechanicWeb | HTTP/2 | 152.2 | 60 ms | 153 ms | 176 ms | 0 / 180 |
| Hetzner CX23 | HTTP/1.1 | 143.3 | 57 ms | 123 ms | 124 ms | 0 / 180 |
| HostXNow | HTTP/2 | 137.7 | 47 ms | 217 ms | 221 ms | 0 / 180 |
| Hetzner CX43 through Tunnel | HTTP/2 | 109.5 | 83 ms | 209 ms | 209 ms | 0 / 180 |
| Hetzner CX43 direct | HTTP/2 | 99.5 | 70 ms | 246 ms | 249 ms | 0 / 180 |

The Ryzen shared hosts are quick. Cloudflare Pages is steadier under this particular burst. The direct-origin and Tunnel result also demonstrates why connection handling, protocol and route matter as much as the server's CPU label.

An older ApacheBench HTTP/1.1 run made Cloudflare Pages appear much slower. Repeating the test with HTTP/2 reversed that conclusion, so the HTTP/1.1 result is deliberately excluded from the ranking.

## Full first-party homepage fixture

The second fixture is the real Fire Pixel homepage design rather than a synthetic 6 KB page. Its deployment bundle is 329,864 bytes across 19 hashed source files, plus the manifest itself. It includes the responsive editorial image, production CSS, five WOFF2 font weights, five WOFF fallbacks and all image candidates. Google Tag Manager, CookiePal and Clarity are removed so third parties cannot mask the hosting result.

A normal 1365×768 Chrome visit selects one AVIF image and WOFF2 rather than downloading every fallback. It made nine network requests and transferred about 103–106 KiB on the compressed HTTPS mirrors. The HTTP/1.1 CX23 transferred about 140 KiB. All 19 manifest files were also fetched from every public mirror and verified byte-for-byte with the expected MIME type. Every timed visit returned HTTP 200, loaded the image, used the Fire Pixel canonical, made zero external requests and recorded zero failures.

### Six simultaneous full pages

Each mirror received three trials of six simultaneous pages in isolated browser contexts: 18 full page loads per mirror, 108 total. The table reports median completed pages per second across the three trials and p95 load time across all 18 pages.

| Mirror | Pages/s | p95 load | Failures |
| --- | ---: | ---: | ---: |
| Cloudflare Pages | 10.79 | 292 ms | 0 / 18 |
| GitHub Pages | 10.36 | 296 ms | 0 / 18 |
| Hetzner CX43 through Tunnel | 10.03 | 335 ms | 0 / 18 |
| MechanicWeb | 9.90 | 309 ms | 0 / 18 |
| Hetzner CX23 | 9.17 | 361 ms | 0 / 18 |
| Hetzner CX43 direct | 8.80 | 399 ms | 0 / 18 |

The direct route did not beat the Tunnel. Both routes share exactly the same CX43 backend, yet the Tunnel was 84 ms faster on median cold LCP and 64 ms better at p95 under the six-page trial. Removing a Tunnel is therefore not automatically an optimisation; the complete TLS and connection path has to be measured.

## Real homepage: Lighthouse 13.4.1

The complete Fire Pixel homepage was deployed byte-for-byte to the Hetzner/Tunnel production route and Cloudflare Pages. Two live desktop runs after optimisation produced:

| Route | Performance | FCP | LCP | CLS | TBT | Server response |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Hetzner through Tunnel | 100 | 282 ms | 382 ms | 0.00 | 0 ms | 80–81 ms |
| Cloudflare Pages | 100 | 250–258 ms | 351–356 ms | 0.00 | 0 ms | 66–70 ms |

The edge copy was about 30 ms ahead on desktop LCP in these samples. Earlier repeated mobile runs were also 100/100, with median simulated LCP of 1.32 s on production and 1.16 s on Pages. Those are small differences, not evidence that visitors can reliably perceive one host as faster.

The audit did find and fix a real homepage problem: late-loading font weights caused repeatable desktop CLS around 0.07. Preloading the weights reduced CLS to exactly 0.00 across three local confirmation runs and four live confirmation runs, moving desktop performance from 99 to 100.

## Cold and warm browser loads

Five fresh-browser pairs from Dublin produced these medians:

| Route | State | TTFB | FCP/LCP | Load event |
| --- | --- | ---: | ---: | ---: |
| Hetzner through Tunnel | Cold | 136 ms | 244 ms | 1,117 ms |
| Cloudflare Pages | Cold | 144 ms | 244 ms | 1,109 ms |
| Hetzner through Tunnel | Warm revisit | 0.6 ms | 32 ms | 81 ms |
| Cloudflare Pages | Warm revisit | 61 ms | 92 ms | 152 ms |

The cold visit is effectively tied. The warm difference is cache policy, not compute: the production HTML was reused from browser memory, while Pages revalidated its HTML. Fingerprinted `/_astro/` assets on Pages now have an explicit one-year immutable browser policy; HTML remains revalidated so the benchmark does not turn the Tunnel route into a cached static edge response.

## Why hosting barely changes the visible page

The final desktop waterfall contained 25 requests and about 506 KB. Only nine requests and 109 KB were first-party. Roughly 78% of transferred bytes came from Google Tag Manager, CookiePal, Clarity and their related endpoints.

That is the strongest practical finding: once the first-party site is already fast, third-party JavaScript and measurement choices can outweigh the hosting difference.

## Honest takeaway

The useful lead-magnet claim is not “edge destroys a 9950X.” The evidence says:

> A static edge, a Ryzen shared host and a small VPS can all make a 6 KB page feel instant. The winner changes when you test one request, tail latency, HTTP/2 concurrency, cache policy or the full browser waterfall. Configuration and third-party payload usually matter more than the CPU badge.

The stronger headline for the full fixture is:

> We put the same visual homepage on an edge, a Ryzen shared host and two VPS routes. The small page hid the difference; the image-and-font waterfall exposed it. The fastest CPU label did not decide the winner—HTTP/2, compression and the connection path did.

## Limits

- One client location is not a geographic benchmark.
- The burst is deliberately modest and does not establish maximum origin capacity.
- Shared-host results can vary with neighbouring tenants and provider controls.
- The CX23 endpoint is HTTP rather than equivalent public HTTPS, so it is shown but not directly ranked against the TLS routes.
- Lab Lighthouse scores are synthetic; eligible Chrome UX Report field data should be added after the mirrors have enough real traffic.
- The full fixture was not yet live on HostXNow, so no 9950X visual-page result is claimed in this snapshot.
